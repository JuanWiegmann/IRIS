# Context Dump — Session 2026-07-22

## What Was Decided This Session

### Architecture (MAJOR SHIFT)

IRIS is NOT a local-LLM multi-agent system. It is a **pure MCP server** (logic + data):
- No Ollama, no Bedrock client, no internal LLM
- The user's LLM (Claude, Copilot, ChatGPT) does ALL reasoning and response generation
- IRIS only provides: personalization context + validation + light cross-session memory

### Scope

IRIS provides personalization + light memory. It does NOT:
- Execute tasks (write emails, analyze Excel — the LLM does that)
- Orchestrate workflows (no Workday, no calendar)
- Replace tools

IRIS answers: "Here's HOW to talk to this user" — not "DO this for the user."

Example: User asks LLM to analyze Excel → LLM does the analysis → LLM asks IRIS "how should I present this?" → IRIS says "bullet points, German, concise, action items first"

### The Self-Check Pattern

`check_draft` is a blind validator. The LLM calls it thinking it's an external service. IRIS validates against profile rules without knowing why the LLM wrote what it wrote. This produces unbiased feedback the LLM couldn't give itself.

### Onboarding System (Target-Based GATE)

IRIS defines research-backed TARGETS (what to learn about the user). The LLM freely decides HOW to reach each target (question strategy, phrasing, order). 

Targets have BARRIERS — minimum evidence needed before they count as "satisfied." Based on Wu et al. 2024, GATE (ICLR 2025), and Westhaeusser et al. 2025.

Key insight from Wu et al.: User OUTPUTS (past writing) drive personalization, not user INPUTS (past questions). Store what users wrote/chose/approved. Serve most-relevant-first.

### Two Layers

- **Layer 1:** Any MCP client. Tools + Anleitung (protocol instructions the LLM follows)
- **Layer 2:** Advanced clients (Claude). MCP sampling — IRIS orchestrates multi-step flows with fresh context per "agent role." User's LLM still does compute.

### Tool Design

Tools start broad (`get_context`, `check_draft`, `onboard`, `log_output`) and split into finer granular tools as implementation reveals usage patterns. E.g., `onboard` later becomes: `get_targets()`, `store_insight()`, `get_missing_info()`, `check_satisfied()`, etc.

## Research Papers Referenced

1. **GATE** (Li, Tamkin, Goodman, Andreas — ICLR 2025)
   - LLM-driven preference elicitation
   - Three strategies: edge-case scenarios, binary yes/no, open-ended
   - Users can't introspect preferences — forced choices reveal tacit knowledge
   - 5-minute interaction window is optimal

2. **Multi-Agent Personalization** (Westhaeusser, Minker, Zepf — arXiv 2510.07925)
   - Four-agent pipeline: Coordinator → Operator → Validator → Generator
   - Multi-tiered memory: STM, Summaries, LTM (embeddings + semantic tags)
   - Dynamic user profile built implicitly from interactions
   - 96% retrieval accuracy vs 87% RAG baseline

3. **User Profile Roles** (Wu, Shi, Rahmani, Ramineni, Yilmaz — arXiv 2406.17803)
   - User OUTPUTS are the primary personalization driver (not inputs)
   - Output-only format fits 2-5x more examples in context
   - Most-relevant-first ordering significantly improves quality
   - Semantic similarity from non-user sources can HURT performance
   - Position in context matters — best examples go first
